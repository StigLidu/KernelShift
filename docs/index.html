Getting started

Introduction

KernelShift is a benchmark environment for coding agents that write optimized AArch64 kernels for Neon, SVE, SVE2 and SME2.

Each task is a kernel from a production library with a reference implementation, workloads taken from real models, and an expert implementation to beat. Through MCP tools, the agent compiles its kernel, tests and times it, and reads the generated assembly, all on the target processor. A kernel scores only if it is correct on every workload, and its score is the speedup over the expert implementation.

QuickstartCheck and time one kernel on your own computer. Task formatDefinitions, workloads, solutions and traces. Processors and extensionsWhich processor runs which instruction-set extension. Run an agentClaude Code, Codex, nanobot and others on EC2.

How a run works

Every harness talks to a KernelShift server over MCP and gets the same tools. The server runs on a cloud instance with the target processor, one per target, and the harness reaches it through an SSH tunnel. Each call compiles, checks and times the code right there, and the result goes back to the agent.

Where the kernels come from

SourceKernelsExpert reference
ncnnConv2D, depthwise Conv2D, pooling (FP32, INT8)ncnn's Neon kernels
llama.cppGEMM (FP32 to 4-bit), RMSNorm, attention, MoEggml CPU kernels
Arm SIMD LoopsStandalone loops loop_001 … loop_223Arm's hand-written SVE, SVE2 and SME2 versions
KleidiAIGEMM and convolution micro-kernelsArm's vendor micro-kernels

The tasks live in the Hugging Face dataset arm-bench/arm-bench-trace. Its TASKS.md lists, for every definition, the expert baseline on each hardware tier and whether it runs there.

Getting started

Installation

You need Python 3.12 or later and clang++. Apple clang works on macOS.

Get the code and the dataset

shell
git clone https://github.com/ArtificialRay/KernelShift && cd KernelShift
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
hf download arm-bench/arm-bench-trace --repo-type dataset --local-dir bench-trace

Check that the dataset loaded

Every tool reads the dataset from bench-trace/.

$ python -m bench.cli summary
{
  "definitions": 142,
  "solutions": 452,
  "workloads": 1942,
  ...
NoteRunning an agent needs an AWS account as well: see Run an agent. Checking and timing a kernel does not.

Getting started

Quickstart

Compile a solution, check it against the reference on every workload, and time it. No AWS account or agent is involved.

Run one kernel

shell
python -m bench.cli bench --definition loop_001 --solution reference_loop_001 --dataset simd-loop --isa sve

Each line is one workload: its id, the verdict, the minimum and 5th-percentile time, and the largest absolute and relative error against the reference.

  6bfe094b  PASSED  min=9.08us  p5=9.15us  max_abs=0.00e+00  max_rel=0.00e+00
  06735e72  PASSED  min=43.30us  p5=43.82us  max_abs=0.00e+00  max_rel=0.00e+00
  ...

Pick a processor that has the instructions

Scalar and Neon code runs on any 64-bit Arm processor. SVE needs Graviton3, SVE2 needs Graviton4 and SME2 needs Apple M4. An SVE kernel run on Apple silicon fails with RUNTIME_ERROR ... SIGILL.

See what there is to run

python -m bench.cli list-definitions
python -m bench.cli list-solutions

Concepts

Task format

A task is four kinds of file in bench-trace/. Every evaluation writes a fifth: the trace.

bench-trace/
  definitions/<op_type>/<name>.json            # what to compute, with a Python reference
  workloads/<op_type>/<name>.jsonl            # concrete sizes and inputs, one per line
  solutions/<dataset>/<author>/<op_type>/<name>.json  # an implementation
  tensors/<op_type>/<name>/*.npy              # inputs captured from real model runs

Definition

The shapes, dtypes and tags of one kernel, and a NumPy reference that defines correct output. Axes are either var (set per workload) or const (baked into the kernel). This is rms_norm_fp32_d2048 from llama.cpp:

{
  "name": "rms_norm_fp32_d2048",
  "op_type": "rms_norm",
  "tags": ["status:active", "model:qwen1.5-moe-a2.7b", "baseline-solution:llama.cpp"],
  "axes": { "M": { "type": "var" }, "D": { "type": "const", "value": 2048 } },
  "inputs":  { "x": { "shape": ["M", "D"], "dtype": "float32" },
               "weight": { "shape": ["D"], "dtype": "float32" } },
  "outputs": { "output": { "shape": ["M", "D"], "dtype": "float32" } },
  "reference": "def run(x, weight): ..."
}

Workload

One line per concrete size. Inputs are generated (random, seeded by the workload id) or loaded from a captured tensor.

{"axes": {"M": 6}, "inputs": {"x": {"type": "random"}, "weight": {"type": "random"}},
 "uuid": "4afccae94503552f86d5d6afeba0bdc0"}

Solution

Source files plus a build spec. Every task ships two: reference-scalar, plain C++ that is the agent's starting point, and the library's own kernel (for example baseline-llamacpp-arm), which the agent has to beat. The agent edits only kernel.cpp; the harness adds the binding files.

{
  "definition": "rms_norm_fp32_d2048",
  "dataset": "llama.cpp",
  "author": "reference-scalar",
  "spec": {
    "language": "cpp",
    "target_hardware": ["graviton3", "aarch64-sve"],
    "entry_point": "rms_norm.cpp::armbench_entry_rms_norm",
    "isa_features": [],
    "compile_flags": ["-O2", "-std=c++14"]
  },
  "sources": [ "rms_norm.h", "rms_norm.cpp", "kernel.cpp" ]
}

Trace

The record of one solution evaluated on one workload: the verdict, the correctness metrics, the timing samples, and the timing protocol they were taken with. Traces from different protocols are never compared.

Tags that change evaluationcorrectness:sqnr switches the check from element-wise tolerances to a signal-to-quantization-noise floor, and e2e:<model> marks the kernels spliced into llama.cpp for the end-to-end runs.

Concepts

Processors and extensions

Each instruction-set extension is a separate target, chosen with --isa. It compiles with its own flags and runs on an EC2 instance whose processor has those instructions. Settings come from config/kernel_contracts.yaml.

ExtensionCompile flagsFeaturesInstance (processor)
Neon-march=armv8-a128-bit Advanced SIMDc7g.xlarge (Graviton3)
SVE-march=armv8.2-a+svesve, dotprod, i8mm; 256-bit vectorsc7g.xlarge (Graviton3)
SVE2-march=armv9-a+sve2sve, sve2, dotprod, i8mm; 128-bit vectorsc8g.xlarge (Graviton4)
SME2-mcpu=apple-m4sme2; 512-bit streaming vectors, ZAmac-m4.metal (Apple M4)

Each extension includes the one before

A solution that declares isa_features: ["sve"] also runs on the SVE2 target, because SVE2 is a strict superset of SVE. The rule stops at SME2.

Why SME2 uses -mcpu=apple-m4

No Graviton processor implements SME, so the SME2 target runs on Apple M4. Its cores run SVE instructions only in streaming mode. With -march=armv9-a+sme2, plain SVE code compiles and then dies with SIGILL; -mcpu=apple-m4 rejects it at compile time, which gives the agent an error it can act on.

CostAn M4 needs an EC2 Dedicated Host, which AWS bills for at least 24 hours. Provisioning never allocates one: allocate it yourself and release it when done.

Concepts

Scoring

A version counts only if it is correct on every workload. Among correct versions, the score is the speedup over the expert kernel.

Correctness

Each workload's output is compared with the definition's reference. Most kernels use element-wise absolute and relative tolerances set per op type. Quantized kernels tagged correctness:sqnr must reach a signal-to-quantization-noise floor set relative to what the reference implementation itself scores on that workload. evaluate stops at the first failing workload.

Timing

  • 10 warmup samples, then 50 timed samples; the score uses the minimum.
  • Each sample repeats the kernel until it lasts at least 10 ms (inner_iters: auto), so short calls are not lost in timer noise.
  • The expert kernel is timed the same way on the same processor.
  • Each run uses one core and its own process.

Speedup@40

For one kernel, the speedup of a version is the geometric mean over workloads of expert time divided by kernel time. Speedup@40 is the best speedup among correct versions within the first 40 tool calls. A benchmark result is the geometric mean of Speedup@40 over kernels, reported with the share of kernels above 1.0.

Every kernel has a scoreA session starts by compiling the scalar starting point unchanged and evaluating it, so even a run that never finds a faster version is scored.

Guides

Run an agent

test_scripts/bench_fleet.py starts an EC2 instance for the target extension, runs the agent on every definition you name, and copies the results back.

shell
python3 test_scripts/bench_fleet.py --harness claude-code --model claude-opus-4-8 \
    --dataset simd-loop --isa sve --definitions "loop_001 loop_002"

--dataset is ncnn, simd-loop, llama.cpp or kleidiai. Without --definitions every definition of the dataset runs. --max-iterations (default 40) caps the compile, evaluate and disassemble calls per kernel.

Results

Each kernel gets agent-runs-<author>/<definition>/, where the author is <harness>-<model>-<isa>:

  • v1.cpp, v2.cpp, …: every version the agent compiled;
  • trajectory.jsonl: one line per tool call. A passing evaluate carries time_speedup_geomean.
Spot by defaultInstances are spot unless you pass --on-demand. A Linux instance shuts itself down within about 2 hours of its driver stopping.

Reference

MCP tools

The tools every harness sees. They behave the same across harnesses and processors; the server runs on the instance being tested.

ToolArgumentsWhat it doesReturns
check_progressdefinitionLooks up the best result so far on this definition.Its version, metrics and code.
compiledefinition, codeCompiles the agent's kernel.cpp; the harness and binding files are added automatically.A version number, or the compiler error.
evaluatedefinition, versionChecks correctness on all workloads, stopping at the first failure; if correct, times the kernel. A new best result is saved at once.Errors, or speedups.
disassembledefinition, version, optional fnDisassembles the kernel entry symbol, or fn.Up to 300 lines of AArch64 assembly.

Use your own harness

Start the server on an instance and point any MCP client at the printed endpoint:

python3 skills/launch/launch_session.py launch --isa sve --dataset ncnn --author my-agent
